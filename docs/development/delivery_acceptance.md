# 第一阶段交付与验收

## 范围和入口

用户端采用 QML，管理端保留 PC 界面。两端通过同一个 ServerRuntime 工作线程中的
Service/Repository 访问同一 SQLite 文件。用户端没有自己的业务数据库。
Web/ECharts、机器学习按本轮确认暂缓，不计作已经实现。

`charging-client` 默认真实 TCP；`CHARGING_CHANNEL=mock` 仅供开发测试，不用于验收。
旧 Widgets 用户端默认不构建，仅在明确传入 `CHARGING_BUILD_WIDGETS_CLIENT=ON` 时构建为
`charging-widgets-client`，避免与正式入口混淆。

## 构建

使用 Ubuntu 22.04、Qt Framework **6.2.4**、C++17，安装包列表见 README。
不要把 Qt Creator 的版本号当作 Framework 版本。执行：

```bash
bash scripts/verify_delivery.sh
```

脚本以 Release 构建，强制 QML、精确 Qt 6.2.4，执行完整测试和数据库校验。
默认构建目录是 `build-delivery`；可传其他构建目录作为第一个参数。
构建成功不等于真实腾讯地图已完成验收，地图还需要下面的合法 Key 和网络检查。

## 启动与数据源

在仓库根目录开两个终端：

```bash
./build-delivery/server/charging-server --address 127.0.0.1 --port 9527 \
  --database ./runtime/acceptance.sqlite3 --demo-seed
```

```bash
./build-delivery/client/charging-client --host 127.0.0.1 --port 9527
```

这是明确选择的演示库，不要对已有重要业务库使用 `--demo-seed`。
初始化不会通过删除数据库来“重置”既有数据。需要全新演示时选择一个新的数据库文件名。
新手机号注册余额为 0；演示用户 `13800138000` 的初始余额为 100.00 元。
演示管理员 `admin / 123456` 仅用于实训；不要将该密码用于公开运行的服务。

两程序位于同一 Ubuntu 虚拟机时使用 127.0.0.1；分别位于不同计算机时，Server 指定实际
局域网监听地址，Client 的 `--host` 指向该地址，并仅对验收局域网开放 TCP 9527。
当前协议不提供 TLS，不适合直接暴露到公网。

## 地图配置

启动客户端之前，由使用者配置自己的腾讯地图 Key：

```bash
export TENCENT_MAP_API_KEY='自己的地图Key'
```

如控制台启用 WebService 签名校验，再配置 `TENCENT_MAP_SECRET_KEY`，不要提交任何真实密钥。
JavaScript 底图使用独立 Key 时配置 `TENCENT_MAP_JS_KEY`；未设置时使用上述 API Key。
需授权地址编码、驾驶和步行路线接口，以及页面使用的地图 JavaScript API。
网络或权限错误会明确显示，不会把示意图、固定起点或伪造路线当作查询成功。
附近站点按手动地址解析后的坐标计算**直线距离**排序；导航里程以路线服务返回值为准。
密钥是否有效、当前额度及实际底图能否加载，需要在验收环境联网检查。

## 必跑的人工闭环

1. 管理端登录。记录本次数据库路径、现有用户数、空闲电桩数。
2. QML 输入一个新的 11 位手机号。确认自动注册、昵称默认规则、初始余额为 0。
3. 修改昵称、选择本地图片上传头像；退出再登录，确认信息仍在。
4. 充值 10.00 元；客户端记录和余额变化，管理端用户/充值记录显示同一笔数据。
5. 选择地区并输入地址定位；确认附近电站距离排序、价格、可用桩数及桩详情。
6. 打开导航，分别选择驾驶/步行；起点必须是刚选择的地址，目的地必须是该电站。
7. 预约空闲桩，确认预约及订单编号；开始充电，功率、电量、时长、金额更新。
8. 正在充电时退出再登录，恢复原充电订单；不能再次占用另一支桩。
9. 停止充电后进入待支付；再次预约应引导处理原订单，不能绕过结算。
10. 支付一次，再重试：只扣款一次；订单完成、电桩空闲，管理端订单金额、用户余额及桩累计次数一致。
11. 管理端刷新，检查日/月统计、真实趋势图、五类电桩状态、用户注册时间和单站在线率。
12. 新建预约后关闭客户端，等超过 15 分钟；仅管理端刷新也应显示预约过期、订单取消、电桩恢复空闲。
13. 管理端冻结无活动订单的用户，确认该用户不能继续操作；解冻后重新登录恢复。
14. 断开服务端，客户端给出明确错误并清理旧会话；重启后重新登录，不显示上一个用户的缓存数据。

服务端充电设备为实训模拟：根据额定功率和服务端时间计费，不声称连接了真实硬件。
人工验证请记录截图和测试账号，不要把示例账号的预置数据当成刚操作生成的数据。

## PR 边界与合入顺序

本轮按数据库 → 业务通信 → 管理端 → QML 客户端分成依赖串联的 PR。
后一个 PR 的 base 是前一个分支，以便差异只显示本板块。前一个合入 develop 后，将下一个
PR 的 base 切回 develop，再重新跑严格 CI。未授权自动合并任何 PR。

完整联调代码位于最后一个分支 `feature/delivery-qml-client`，可以提前验收。
先用 `git worktree list` 查看该分支是否已在某个工作目录检出：若已检出，直接打开对应目录，
在该目录更新即可，不需要再次切换分支，也不要强制解除工作树占用。

```bash
git fetch origin
git pull --ff-only
```

若该分支尚未在其他工作目录检出，再在准备验收的仓库目录执行 `git fetch origin`、
`git switch feature/delivery-qml-client` 和 `git pull --ff-only`。
