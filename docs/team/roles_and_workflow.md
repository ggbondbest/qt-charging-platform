# 五人角色与协作流程

状态：阶段 0/1 协作基线

## 1. 第一阶段范围

第一阶段只交付三个能够联动运行的部分：

```text
Qt 充电用户端
        ↓ Socket
Qt PC 服务端
        ↓
SQLite 数据库
```

Web 大数据可视化和机器学习智能分析暂缓。只有前三部分基础功能完整、业务闭环稳定后，才由全组共同决定是否追加扩展模块。

共同目标是完成“手机号登录/自动注册 → 找站找桩 → 预约 → 充电 → 停止 → 计费 → 结算”，并让 PC 管理端能够看到一致的用户、设备和订单状态。

## 2. 角色与模块负责人

在成员姓名和 GitHub ID 确认前，统一使用“组长、成员2、成员3、成员4、成员5”称呼，不在仓库中猜测账号。

| 角色 | 主责范围 | 必须共同确认的接口 |
|---|---|---|
| 组长 / TL | 系统架构、Socket、多线程、公共协议、核心充电流程、计费与订单状态、系统集成 | 公共模型、状态机、跨模块接口、发布版本 |
| 成员2 | 用户端登录、附近电站、地址搜索、距离排序、电站详情、地图导航 | 登录响应、电站/电桩查询协议、地图配置 |
| 成员3 | 个人中心、头像昵称、充值、订单、充电和结算页面 | 用户资料、充值、充电状态和结算协议 |
| 成员4 | 管理员登录、Dashboard、营收图表、电桩/电站/用户/订单管理 UI | 管理端查询、筛选、状态变更接口 |
| 成员5 | Schema、Seed、Repository、事务、索引、测试数据和数据库文档 | 表字段、约束、事务边界、Repository 接口 |

负责人不是唯一可修改者，而是负责保证本模块的设计一致、PR 可合并、文档和测试同步。跨模块需求必须在编码前由相关负责人确认。

## 3. Review 关系

默认交叉 Review 关系为：

- 成员2 Review 成员3的用户端 PR，成员3 Review 成员2的用户端 PR。
- 成员4 Review 成员5的后台/数据 PR，成员5 Review 成员4的后台 PR。
- 组长 Review 公共模型、Socket、线程、数据库接口、状态机、CMake、配置和跨模块 PR。
- PR 作者不能批准自己的 PR。
- 涉及两个模块时，至少邀请两个模块中的另一位负责人；核心契约还需要组长批准。

Review 不只检查界面能否打开，还应检查：

- 是否符合已确认的候选模型、状态和协议。
- Socket 是否正确处理字节流、错误和断线。
- QObject、线程和数据库连接是否在正确线程使用。
- 订单、余额、电桩和预约状态是否保持一致。
- 是否引入 Qt 6.2.4 不支持的 API。
- 是否有可复现的测试步骤，异常路径是否被覆盖。

## 4. 分支与合并流程

```text
master（稳定版本）
   ↑ 发布 PR
develop（集成版本）
   ↑ 功能 PR
feature/<area>-<topic>（短期任务）
```

标准流程：

1. 在任务开始前确认负责人、接口、输入输出和验收条件。
2. 从最新 `develop` 创建 feature 分支。
3. 优先提交最小可 Review 的实现，避免一次 PR 同时修改多个模块。
4. 本地完成构建、测试和自查后推送分支。
5. 创建目标为 `develop` 的 PR，附测试证据和必要截图。
6. 由指定成员 Review，作者修复所有阻塞问题。
7. PR 合并后立即在 `develop` 联调，不等待所有模块全部完成。
8. 阶段功能稳定后，由组长创建 `develop` 到 `master` 的发布 PR。

禁止：

- 直接在 `master` 或 `develop` 编码和推送。
- 五个人各自维护长期个人分支。
- 在 feature 分支中自行复制公共模型、协议或数据库结构。
- 为解决冲突而覆盖或删除其他成员的有效修改。
- 未经 Review 将临时演示代码、假成功返回或硬编码数据合入稳定分支。

## 5. 接口先行规则

以下内容必须先形成小型契约 PR，再由各模块并行实现：

- 公共领域模型和字段类型。
- 电桩、订单、预约和用户状态集合。
- Socket 帧格式、请求类型、响应和错误码。
- Schema、外键、唯一约束、事务边界和 Repository 方法。
- 配置键、资源路径和公共 UI Token。

契约变更 PR 必须说明：

1. 为什么需要修改。
2. 哪些 Client、Server、Database 模块受影响。
3. 是否保持旧消息或旧数据兼容。
4. 哪些文档和测试同时更新。

契约合并后，受影响成员应尽快同步 `develop`。同一个字段不得在不同模块使用不同名称、单位或状态值。

## 6. 高冲突文件责任

| 路径/内容 | 默认把关人 | 变更要求 |
|---|---|---|
| 根 `CMakeLists.txt`、公共构建选项 | 组长 | 单独说明跨平台和 Qt 6.2.4 影响 |
| `common/` 模型、协议、错误码 | 组长 | 契约 PR，加协议或序列化测试 |
| Socket 帧解析和分发 | 组长 | 覆盖半包、粘包、非法长度和断线 |
| `database/schema.sql`、事务接口 | 组长 + 成员5 | 同步数据库文档、Seed 和测试 |
| 全局 QSS、共享图标和资源别名 | 组长 + UI 相关成员 | 避免无关页面样式回归 |
| GitHub 模板与协作规则 | 组长 | 与实际流程保持一致 |

## 7. 每日协作节奏

建议每天进行一次不超过 15 分钟的同步，只报告：

- 昨日已经完成且可验证的结果。
- 今日准备完成的一个主要目标。
- 当前阻塞及需要哪位成员提供接口或 Review。
- 是否修改公共协议、Schema、资源或 CMake。

任务状态统一使用：`Todo`、`In Progress`、`In Review`、`Blocked`、`Done`。只有代码已合并到 `develop` 且满足验收条件时才能标记 `Done`。

## 8. 阶段顺序

1. 环境、目录、分支、代码风格和 UI Token。
2. 公共模型、状态、协议和 Schema 第一版。
3. 手机号登录最小闭环：Client → Socket → Server → Repository → SQLite → Client。
4. 五人按模块并行，每完成一个可用功能就 PR、Review、合并和联调。
5. 在约 40% 至 50% 进度时完成第一次 Alpha 全流程联调。
6. 按需求清单补齐基础功能和异常处理。
7. 基础功能接近完成后统一 UI，再决定扩展功能。
8. Ubuntu 22.04 全新 clone、清洁构建、启动和完整演示。

第 3 步的手机号登录闭环已经提供公共 Socket、Service、Repository 和 SQLite 运行时边界。
成员可在各自目录基于候选接口并行开发，不得重复实现公共基础层。严格 CI 已通过；跨模块
真实联调和公共契约冻结仍需五人确认，再由组长记录结论。

## 9. Definition of Done

一个任务只有同时满足以下条件才算完成：

- 行为满足任务验收条件，不是静态页面或假数据占位。
- 在 Qt 6.2.4、C++17 下成功编译。
- 正常路径和相关异常路径已验证。
- 新业务逻辑有适当测试，或在 PR 中说明无法自动化的原因和手工步骤。
- UI 变更有截图，且布局在目标平台可用。
- 协议、Schema、配置和公共模型变更已同步文档。
- 未引入绝对路径、密钥、运行时数据库、构建产物或无关改动。
- 至少一名非作者完成 Review，所有阻塞意见已解决。
- 已合并到 `develop` 并完成最小集成验证。
