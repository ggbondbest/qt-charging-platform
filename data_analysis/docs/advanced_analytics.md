# 多维运营分析与答辩展示

本次重点是把「统计了多少」升级成「哪些群体、哪些时段、哪些环节不同，以及差异是否有足够样本支持」。
不是把同一列换几种图，也不把指标数量称为分析维度。

## 1. 数据是否足够，为什么不重新随机造一批

沿用当前已清洗、已经绑定模型和 MySQL 发布批次的 180 天数据：5 城市、25 电站、75 电桩，
23 类原始表约 583 万行。其中有约 12.2 万次充电会话、16.9 万次尝试、388.8 万条五分钟遥测，
另有用户/车辆、预约/排队、支付/退款、维修、价格、节假日和气象。

这些表已经能回答多维运营问题。再次扩大随机行数并不能提高分析质量，反而会使原模型、发布批次和界面口径失配。
所以新增的是独立、可追溯的 **Spark 多维分析成果包**，不改原数据、模型或数据库。

数据边界：充电业务是按行为规律校准的模拟数据；气象使用 ERA5 真实历史再分析数据；
**没有使用 Caltech ACN-Data 实测充电会话，不能在答辩中称为真实国内充电运营结果。**

设计参考：

- [多城市电动车使用行为实证研究](https://www.nature.com/articles/s44333-024-00023-3)启发了城市、车辆类型、日类型与时段的联合分层。研究对象与本项目模拟数据不同，不能直接转用其统计结论。
- [Caltech ACN-Data 官方说明](https://ev.caltech.edu/dataset)提供真实会话时间、电量等字段，可作为后续独立外部验证集。本轮不把它与国内模拟的价格、排队、支付、用户标签硬拼接。
- [ECharts visualMap](https://echarts.apache.org/handbook/en/concepts/visual-map/)支持用位置、颜色、大小共同表达维度；[Dataset/encode](https://echarts.apache.org/handbook/en/concepts/dataset/)用于一致映射轴与提示。多维不等于必须画三维立体图。

## 2. 分析问题、计算方法与图表

| 运营问题 | 语义维度与处理 | 展示及可解释信息 |
| --- | --- | --- |
| 什么时候、哪类站最忙？ | 城市→电站/站型×星期×小时；UTC 转上海业务时间；构建完整小时网格；完整样本加权 | 星期/小时热力图，颜色为利用率；同时提供平均单站负荷、电量、完整站点小时样本数 |
| 高电量是不是高效率？ | 电站×时间×站型，联合遥测、排队解决事件、会话连接时长、现金事件 | 气泡位置为利用率/平均等待，大小为电量、颜色为站型；可识别忙而低周转的站 |
| 天气与需求有何关联？ | 城市/站型×5℃温度区间×小时；按城市及同一小时连接真实气象 | 温度/时段热力图，附样本数；切到同城、同站型再比较，避免把地域差异误作温度效应 |
| 谁需要频繁补能，每次充多少？ | 同一用户全网相邻开始时间窗口→本次会话所在城市/电站/站型/日期→用户类型×间隔档位或电量档位 | 可切换的补能行为分布；颜色为同类型内占比，同时展示次数与平均值；首条无前序记录单独计数，不当作零间隔 |
| 服务机会具体因为什么流失？ | 一次尝试→唯一入口（直接/排队/预约）→成功开始或具体失败原因；保留无可用桩、等待离队、叫号未确认等差异 | 三阶段 Sankey、失败原因排序和各入口成功率；原因占比以未成功尝试为分母，入口成功率以该入口全部尝试为分母 |
| 哪类站、哪个小时需要进一步排查？ | 站型×本地小时×尝试成功率，按城市/电站/日期筛选；同格关联排队加入、会话开始、遥测与接口配置 | 成功率热力图点击联动：样本量、失败原因、平均等待、充后占位、利用率、AC/DC配置；少于30次标为小样本，无尝试留空而不是0% |
| 不同使用群体有什么差别？ | 站型×用户类型×电池容量档位×AC/DC接口；联合四维分组；计数、电量、充电/占位时长 | 多层旭日图；面积是会话数量，不是收费；明细提供电量、有效时长样本均值 |
| 哪些指标共同变化？ | 站点日面板中利用率、等待、充后占位、成功率、温度的成对有效样本 | Pearson 相关矩阵；显示 n，常量/不足3对留空，不作因果、显著性或收益保证 |

原有总览的地图、KPI、柱状图、折线图与状态环图保留。
新增分析按「时空与效率」「用户与服务」组织，避免把十几张图堆成一条长页面。
站型筛选、电站下钻和所选业务日期共用发布批次；界面显示的数据量与口径来自实际响应。

## 3. 关键统计边界

1. 利用率 = 完整小时内充电样本之和 / 完整小时内全部桩样本之和。不是先算各站百分比再平均。
2. 平均单站小时功率 = 完整小时电量 kWh / 完整站点小时数。它不是全网同时峰值。
3. 遥测缺失的小时不填零；没有排队解决事件时平均等待为空，不能宣称等待 0 分钟。
4. 电量按遥测区间日统计；会话画像按开始日归属整段会话。跨午夜时两者不必相等。
5. 净收款 = 收款 − 退款，不是利润。运营成本、充电占位和队列事件的时间口径不能混淆。
6. Sankey 以所选日期内创建的尝试为同一分母，展示批次最终结果，不冒充历史某刻已知状态；“无可用电桩”不能与“排队超出耐心”合并成笼统的主动放弃。
7. 补能间隔是同一用户本平台全网两次开始时间之差，不是两次订单之间的离站空闲时长。先求历史前序再筛选本次会话，避免切换电站/日期造成伪首条或人为拉长间隔。生成器另有 `vehicle_energy_intervals.external_charge_wh` 记录站外补能，因此平台复充间隔不能当成车辆所有充电的间隔。
8. 行为图按会话/可观测间隔次数加权，不是去重用户占比，也不是新增获客或流失率。高频用户会贡献更多记录；观察结束后尚无下一次记录不代表离开平台。
9. 同城气象复制匹配多座站，样本量是站点小时，不是独立气象观测数。相关分析是描述性探索，可能有站点混杂和序列相关。
10. 原数据的 `vehicle_class` 恰好等于用户类型，因此不能拿它再算一个独立维度；本次改用车辆真实生成容量分档（小于50、50至不足70、至少70 kWh），避免重复分类制造“多维”。
11. 服务成功率按尝试创建小时、等待按排队加入小时、完整会话占位按开始小时归属；利用率是同一小时遥测。并列展示不同事件群体不等于某次失败发生瞬间的资源快照，不能证明占位或接口配置导致失败。接口数与额定功率是静态库存，不能按天数累加。
12. 原首次观察月留存仅保留后台兼容成果，不在主页面展示。固定6,000用户池、全部统计期前注册且没有新增/流失生命周期，用其首次观察月份讲新客留存缺乏业务意义；不能靠修改百分比制造趋势。

## 4. 架构与复现

```text
既有 CLEAN Parquet（只读、SHA256 校验）
  → PySpark 多表连接 / 时间网格 / 窗口去重 / 多维聚合
  → station_day / station_hour / attempt_flow / session_segments
    + user_behavior / service_hour（retention 仅兼容保留）
  → 独立 advanced_manifest.json + JSON.gz + Spark 执行计划
  → FastAPI 校验与 MySQL 当前批次一致，在线仅合并有限聚合行
  → Vue 同批次筛选 → ECharts 联动图表 + 数据明细
```

原 MySQL 仍是发布数据集、基本统计和城市/电站校验的来源。
新增成果包是固定批次的只读分析副本，不是 SQLite 回退或浏览器写死的数据。
API 不扫描 583 万条明细，不加载用户编号，不因文件丢失而返回假图表；文件损坏返回 503，批次不一致返回 409。

在仓库根目录，准备 Python 3.11/3.12、Java 17 和 `requirements-spark.txt`：

```sh
python -m data_analysis.spark_jobs.advanced_analysis \
  --input data_analysis/datasets/analytics_full_180d_v1 \
  --output data_analysis/datasets/advanced_analytics_v2 \
  --master 'local[2]' --driver-memory 2g
```

输出目录必须不存在，避免覆盖证据。已有完整成果无需重算；重算请指定新目录，并通过环境变量
`ANALYTICS_ADVANCED_BUNDLE` 指向它。CLEAN 可先按项目既有 HDFS 验收流程验证后取回，分析包也可归档到 HDFS；
此导出命令的服务副本为本地路径，不声称已经在 Linux/HDFS 上运行。

新接口：`GET /api/v1/dashboard/advanced`，支持 `datasetId/publishedBatchId/cityId/stationId/startDate/endDate/siteType`。
响应的 `provenance/scope/summary` 说明来源、计算批次、查询范围和分母。
完整请求/响应类型在 OpenAPI 和生成的 `contracts/types.ts` 中。

前端照旧 `npm test && npm run build`，启动统一 `python -m data_analysis.delivery.cli serve`；
已有后端进程需重启才会加载新接口。无需重新训练机器学习模型、重建 MySQL 库或修改原数据。

## 5. 建议答辩顺序（约 6 分钟）

1. 展示原始表种类、记录量与数据来源边界；不要只说“数据很多”。
2. 展示[独立清洗挑战](advanced-cleaning.md)的原始异常、修复/隔离、实际命中原因及金额影响。
3. 展示 Spark 七个分析成果表、执行计划和校验清单，解释窗口前序、不同事件小时和一次多表关联如何保留正确分母。
4. 大屏选全部城市→一个城市→某站型，用热力图与气泡图回答忙闲时段及效率差异。
5. 切换补能间隔/单次电量比较用户群体；从桑基图选出主要失败原因，再点击站型×小时成功率格子查看等待、占位和接口结构；展示四层画像补充群体解释。提出待验证的运营方向，而不是把相关性说成因果。
6. 展示气象分层和相关矩阵，解释“相关不等于因果”；最后切到已有机器学习页面演示预测。

评分由老师依据实际验收决定。本升级提供可复现的计算、可解释结果和清楚的数据展示，不以视觉复杂度代替分析有效性。

## 6. 验证方法

- 实际成果的行数、校验和、执行计划与守恒结果见 `datasets/advanced_analytics_v2/advanced_manifest.json`，不要把旧版五表的行数当作新版七表的结果。
- `test_advanced_analysis.py` 用真实 Spark 验证时间边界、前序回看、分类和关联不扩张；`test_advanced_bundle.py` 核对实际交付成果与原始 CLEAN 身份及守恒。
- `test_advanced_api.py` 验证分母、空值、筛选、接口库存不随日期重复计数；前端组件测试验证格子选择联动与过期请求保护。
- 运行中的 MySQL/FastAPI 应对全域和五城市、全期及最近7天交叉检查：新分析电量、开始会话、行为分布会话、服务热力图尝试数应与原总览及对应成果一致。
- 最终环境仍需在 Linux/HDFS 上复验；本地测试和浏览器验收不能替代最终环境验收。

短期内“开始会话数”与“完成会话数”可能不同：前者按开始日期归属，后者按结束日期归属，跨日会话不能据此判为丢失。

## 7. 本轮可直接演示的案例

选择全部城市、`2026-05-23 ≤ 日期 < 2026-05-30`：

- 6,532 次尝试中有 1,744 次未成功开始；无可用电桩 916 次、等待超出耐心 320 次、叫号未确认 153 次。不要再把三者合并为主动放弃。
- 点击社区站型 `19:00–20:00`：170 次尝试中 60 次成功开始（35.3%）；平均等待约27分钟，充电利用率约85.1%，充后占位占比约46.1%；所选5个社区站静态配置为10个AC桩、5个DC桩。
- 正确解读是“社区站晚间可优先复核排队和车位周转，并进一步验证接口配置是否匹配需求”；不能直接断言“多装某种电桩一定挽回多少订单”。
- 同一格子的会话数为61，成功尝试数为60并不矛盾：前者按会话开始小时归属，后者按尝试创建小时归属，排队和预约可能跨小时。
- 点击校园 `05:00`，只有4次尝试，虽显示100%成功，也会提示小样本；`00:00`没有尝试，成功率留空，不显示0%或100%。

这些数字来自固定模拟发布批次，仅作为复现实例。切换城市、日期或批次后，页面必须重新计算，不能把示例数字写死。
