# 多类型脏数据挑战与清洗证据

## 为什么增加这部分

原数据管线已经做了类型约束、格式规范化、关系校验、去重和隔离。新增的不是另一套“特判成功”的清洗器，而是可复现的 **带答案挑战集**：选取现有 CLEAN 样本，主动构造不同质量问题，再调用正式的 `read_table → clean_sessions`，用实际处理结果核对预期。

它回答三个答辩问题：

1. 不只是去空值、去重，还能处理哪些格式、数值、时间、业务和关联错误？
2. 错误数据如果直接求和，会给费用统计造成多大偏差？
3. 隔离错误时，有没有误删原本正确的订单、把缺失值填成假数据，或重复统计？

这是 **故意构造的质量测试样本**，不能把其中的错误占比说成全量数据污染率，也不能把通过率说成未知真实数据上的准确率。原 180 天数据、已发布 MySQL 批次、机器学习输入和原文件哈希都不会被改动。

## 覆盖的 20 类问题

| 质量维度 | 挑战类型 | 处理方式 |
| --- | --- | --- |
| 唯一性 | 同一订单完全重复 | 先校验，再确定性去重；重复副本保留隔离原因 |
| 表示规范 | Unicode 边界空白、状态大小写 | 安全规范化，不改变业务含义 |
| 表示规范 | 全角金额数字 | 转换已知数字表示，仍保留整数“分”单位 |
| 表示规范 | ID 内部零宽字符 | 清除结构化标识中的不可见字符 |
| 时间表示 | 同一时刻改写为明确 `+08:00` 时区 | 正确转换为同一 UTC 时刻；不是异常删除 |
| 类型与范围 | 数字中混入字母、整数溢出、非有限 SOC | 隔离，不能猜测 `O` 是否代表 `0` |
| 时间歧义 | 时间戳丢失时区 | 隔离，不能推断其原时区 |
| 业务约束 | 负费用、结束时间不晚于开始、SOC 超过 100% | 隔离并记录具体规则 |
| 金额一致性 | 总费用不等于电费＋服务费＋停车费－优惠 | 隔离，避免账面费用失真 |
| 完整性 | 缺失订单主键 | 隔离，不自动生成新业务主键 |
| 引用完整性 | 电站 ID 不存在 | 隔离 |
| 归属一致性 | 存在的电桩却关联另一电站、存在的车辆关联另一用户 | 隔离；仅检查外键“存在”不足以发现此类错误 |
| 枚举与目标 | 无效订单状态、非正充电目标 | 隔离，不猜测业务状态 |
| 文本质量 | Unicode 替换字符 `�` | 隔离，不尝试恢复不可知的原始字符 |

表格合并了同一质量维度；实际 `CASES` 中有 20 个独立测试类型。多个规则可能同时命中一行，正式清洗器按固定优先级记录 **一个主隔离原因**，不能把原因计数累加解释成所有问题数量。

## 数据流与保护措施

```text
核验 acceptance_manifest、serving_manifest 和实际消费的 CLEAN 文件 SHA256
  → 按 SHA256(seed:session_id) 排序，选有上限的样本
  → 保存未改动基准 + 确定性注入计划
  → 保存脏 CSV（格式变体替换其表示；非法克隆保留正确原件）
  → 正式 Spark 规范化、校验、确定性去重
  → CLEAN Parquet + quarantine Parquet + 可核对报告
  → 所有断言通过才写 _SUCCESS
```

- 默认 256 条基准订单，最多 4096 条；只将这个有界样本取到驱动进程构造测试记录，不收集全量遥测到内存。
- 关联查询继续使用原电站、电桩、用户、车辆和充电尝试，验证真实的外键和归属关系。
- 输出必须是新的、独立的目录，不允许覆盖、嵌套进输入目录或用符号链接绕过目录边界。
- 基准逐字段与处理后的结果双向 `exceptAll` 比较，不只比较订单数量。金额、时间、用户归属等任何漂移都会失败。
- 每个测试用例通过原始 CSV 记录 SHA256 与实际隔离结果匹配。期望只是测试答案；脚本不会按答案生成“通过”结论。
- 报告不包含原始用户/订单 ID；本地审计 CSV/Parquet 保留原有模拟标识以供追踪，不通过网页暴露明细。
- 保留隔离原始 JSON、实际规则、源记录哈希；不裁剪离群值、不填造金额、不删除原始证据。

## 运行方法

在仓库根目录，使用已有 Java 17、Python 3.11/3.12、PySpark 3.5.6 环境：

```bash
python -m data_analysis.spark_jobs.cleaning_challenge \
  --input data_analysis/datasets/analytics_full_180d_v1 \
  --output data_analysis/outputs/cleaning_challenge_v1 \
  --sample-rows 256 --seed 42 --master 'local[2]' --driver-memory 2g
```

同一输入文件、`seed` 和样本数会选择同样记录并生成同样挑战。生成时间、Spark 输出分片文件名不保证逐字节一致；判断可复现性应核对注入计划、记录哈希、统计结果和断言。再次运行需换一个未存在的输出目录。

若系统有多个 Python，确保工作进程与驱动使用同一解释器。PowerShell 示例（使用已激活环境的 `python`）：

```powershell
$env:PYSPARK_PYTHON = (Get-Command python).Source
$env:RUN_SPARK_TESTS = '1'
python -m unittest data_analysis.tests.test_cleaning_challenge -v
```

Linux 测试示例：

```bash
RUN_SPARK_TESTS=1 PYSPARK_PYTHON="$(command -v python)" \
  python -m unittest data_analysis.tests.test_cleaning_challenge -v
```

这个挑战工具消费 **本地完整验收包**，不直接读取 `hdfs://`。若验收包在 HDFS，先按既有同步流程下载；完成后可将独立证据目录上传 HDFS。上传不等于通过验证，应保留真实的 HDFS 检查结果。

## 产物与讲解顺序

| 文件/目录 | 用途 |
| --- | --- |
| `baseline/charging_sessions.csv.gz` | 未受挑战影响的正确样本，作为独立真值 |
| `injection_plan.json` | seed、案例类型、预期动作、原始记录与源订单哈希 |
| `raw/charging_sessions/` | 实际交给正式清洗器处理的脏 CSV |
| `clean/charging_sessions/` | 正式清洗结果 |
| `quarantine/charging_sessions/` | 隔离副本和实际原因，保留错误原文 |
| `report.json` | 实际 Spark 版本、来源绑定、分类型结果、金额偏差、逐字段恢复和守恒断言 |
| `_SUCCESS` | 所有测试答案与实际结果相符、基准完全恢复、行数守恒后才存在 |

建议先展示一条“外键存在但归属错误”的记录，再展示“无时区时间”和“全角金额”的不同处理：前者不可确定应隔离，后者可以不改变含义地规范化。最后展示 `report.json` 的结果。

报告中金额指标是订单 **账面费用（分）**，不是收款，也不是利润。`beforeNaiveParsedSum` 故意演示忽略质量规则、直接对解析结果求和；无法解析的数值为 NULL，并单列 `nullFeeRows/nullEnergyRows`，不把它们伪装为 0。`afterBillDistortionCents` 应为 0，但必须由实际执行验证，而不是写死。

重点看四项证据：案例的实际命中结果、`inputRows = cleanRows + rejectedRows`、`exactBaselineRestored`、金额偏差前后对照。不要只展示“清洗成功”一个百分比。

## 随仓库交付的实际结果

`datasets/cleaning_challenge_v1/` 保存了这次真实 PySpark 3.5.6 执行的完整小型证据：
256 条基准记录、20 类 256 个挑战案例；460 条输入最终为 256 条保留、204 条隔离，
案例全部符合预期、基准逐字段恢复、零误删。直接忽略质量求和产生的账面费用偏差为 737,836 分，清洗后为 0。
这些是独立挑战的实测结果，不是原 180 天全量数据的错误金额或污染比例。
