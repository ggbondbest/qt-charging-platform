# `ml/reliability/` · 桩级次日启动可靠性预警 / 坏桩巡检排程（第七线）

今晚（比如 22:00）算一遍：明天哪几台桩大概率会出现技术性启动失败，值班员明早按清单去查。
本线把这句话变成一个可复核的模型：**某台桩的明天会不会至少出现一次技术启动失败**（二分类风险分 + 预计失败次数）。

第二阶段"自己找新数据"的产物，样本单位与已有六线**完全不同**：前五线一行一个事件，本线一行是
**一台桩 × 一个北京日历日**。它和第六线最亲（共用同一批技术失败事件作事实来源），但必须硬切割：

| 线 | 样本单位 | 决策时点 | 交付动作 |
| --- | --- | --- | --- |
| `attempt`（第六线） | 一次插枪启动尝试 | `attempted_at`（用户已选好桩） | 这次启动的风险分 → App 提示换桩 |
| **本线（第七线）** | **一台桩的一个北京日历日** | **当日起点之前一刻（今天还没开始）** | **"明天查这几台桩" → 巡检排程** |

第六线决策时点看得见"这次插的是哪根枪"；本线决策时点**一次尝试都还没发生**。这条切割写进
`build_panel` 的结构断言与标签口径，不是口头声明。

## 泄漏纪律（本线最容易死人的一处：当日暴露度）

1. **当日暴露度是标签的同窗量**。实测失败日率按当日尝试数分层：1–2 次 **1.9%** → (2,5] 7.0% →
   (5,10] 29.1% → (10,20] 41.1% → **>20 次 52.9%**（28 倍）。把 `attempts_on_day` 当特征能白拿一大截
   AUC，可它在决策时点还不存在。所以 `attempts_on_day` / `users_on_day` / `started_on_day` /
   `tech_fails_on_day` / `fail_flag` 连同身份键、原始时间戳、标签列全部进 `FORBIDDEN_FEATURES`，
   `pick_features` 再断言一次。允许的是"截至昨天为止"的因果替代：`attempts_per_day_7/14/30/90d` 等。
2. **oracle 基线单列做对照，明确标注不可部署**：真用当天实际尝试次数打分，TEST AUC **0.7870**，
   只看昨天的因果桩先验 0.7820——作弊只多出 **+0.0050**。也就是说当天暴露度里可提前预知的部分，
   因果特征已经从历史里估出来了；剩下的 0.0050 是本线的**理论上限差**，不是已用掉的泄漏。
   滚动研究十轮里逐轮复算同一条（十轮均值 oracle 0.7737 vs 先验 0.7768，**甚至没有跑赢**）。
3. **先验收缩目标必须是因果量**：`(失败数 + α·先验)/(观察数 + α)` 里的先验取"截至该日起点之前的
   全量经验率"（日率先验实测区间 0.0 → 0.21722，尝试率 0.0 → 0.03586），不是全表标签率。
4. **工单与成本**：`status`（全表终态）、`accepted_at`/`work_started_at`（调度侧可读性未定）、
   `labor_cost_cents`/`parts_cost_cents`（修完才知道的钱）、`anomaly_labels`（第四线的事后人工标签，
   整表不读）——全部在 manifest 的 `notRead` 里逐条留了原因；`demand_multiplier` / `weather_hours` /
   `severity` 进 `IGNORED_COLUMNS`（"读过但不用"名单是 **dict**，原因跟着键走，消费方取键即可）。
5. **两条独立路径自证**：`verify_no_future_leak` 随机抽 250 行，用全表布尔掩码（不排序、不二分、
   不 `merge_asof`、不复用 `AsOfCounts`/rolling）独立重算 **17 个**最危险的量，逐条要求 0 偏差。
   本次实测 16 项 `maxAbsDiff = 0.0`，仅 `temp_c_max_mean_30d` 差 **7.1e-15**（浮点加法次序噪声，非逻辑差）。

## 运营口径（阈值怎么选、怎么守预算）

冻结规则（只在 VALIDATION 上选，TEST 只验不改）：**精确率 ≥ 2×VAL 基础率（0.46408）且日均告警
不超预算**（逐日 `max(1, ceil(0.25×在用桩数))` 合计），取满足者中召回最大的阈值；若无档满足则退回
最高精确率档并**如实标注**（本线未触发退回）。实测冻结阈值 **0.442361**。

## 结果（TEST 盲测，一次算完）

> 全部指标为模拟数据测试结果（第二阶段发布批次 `analytics-298aa3ee1401461fb06ea2bb96930dcf`）。
> **特征来自本线新增的派生数据集 `charger_day_panel_v1`（独立目录），是对发布批次真实记录的确定性聚合。**

n = 2,236 桩日（75 桩 × 30 天），正类 486，TEST 基础率 **0.21735**。

**必须如实报告的负结论**：学习的 GBT 在 TEST 上**没打过两行查表就能实现的基线**——
相对查表 **−0.62%**、相对因果先验 **−0.72%**（相对纯用量基线 +3.69% 是模型唯一赢的一档）。
TRAIN 0.8898 → VAL 0.7843 → TEST 0.7763 的差距是过拟合方向，但十轮滚动（见下节）显示这个
"没打过"不是偶然。发布口径因此以便宜基线为准，模型作为对照一并给出。

模型自身的其他 TEST 指标：PR-AUC **0.4362**、LogLoss 0.43596、Brier 0.14482、
lift@5/10/20% = **2.547× / 2.28× / 2.028×**。

| VALIDATION（选阈值） | — | — | 0.46875 | — | — |
| **TEST（只验不改）** | 424 | 18.96% | **0.4410** | 0.3848 | 0.4110 |

**预算合规**：30 天里最大 21 条/天、平均 14.13 条/天（日预算约 18–19 条），超预算 **1 天**

昨天坏了只剩 0.6349（n=486）。与分数的秩相关（Spearman）：因果先验 .9108、回归 .9161、查表 .8967、
纯用量 .7902、oracle .6932——模型和"一行查表"排出来的人本来就是八九成同一批。

中段几乎贴合，**最高两桶系统性高估**（+0.088 / +0.104）：风险分可用于**排序巡检**，

## 十轮滚动重训研究（`rolling.py`）

折设计与第五、六线完全一致：warmup 58 天起，每轮拟合窗后 12 天做评测、窗尾 12 天选特征集与阈值，
58 + 12×10 = 178 天**正好铺满** `mlSplits` 全窗。每轮 JSON 以 O_EXCL 落盘可续跑。口径警告：这些折
**重复用到**了上面那次盲测的 TEST 窗口，轮次均值**不是盲测指标**，只回答"稳不稳、每轮该选哪套、历史会不会变有用"。

| 指标 | 均值 | 标准差 | 首轮 | 末轮 |
| --- | --- | --- | --- | --- |
| 模型 AUC | **0.7629** | 0.0195 | 0.7455 | 0.7754 |
| 同轮查表基线 | **0.7796** | 0.0119 | 0.7624 | 0.7878 |
| 同轮纯因果桩先验 | **0.7768** | 0.0126 | 0.7558 | 0.7861 |
| 只用因果预期用量 | 0.7374 | 0.0215 | 0.7212 | 0.7546 |
| 朴素 lag1 | 0.5841 | 0.0169 | 0.5721 | 0.5991 |
| oracle（不可部署） | 0.7737 | 0.0250 | 0.7760 | 0.7941 |
| 每轮重选阈值 | 0.3948 | 0.0502 | 0.4031 | 0.3908 |

四个结论：

1. **"GBT 打不过一行查表"是显著结论，不是抽样噪声**：逐轮"模型 − 同轮最强基线"为
   `[-0.0169, -0.0230, -0.0550, -0.0274, -0.0068, +0.0043, -0.0166, -0.0052, -0.0114, -0.0124]`，
   10 轮只赢 1 轮，符号检验 **p ≈ 0.0215**（对查表与对因果先验各自都是这个结果）。
   单次盲测的 −0.62% 只是这条分布的中位数附近。
2. **每轮 VAL 选谁也不稳**：10 轮 VAL 选出 staticOnly **6** 次、historyOnly **2** 次、full **2** 次、
   opsOnly **0** 次。本次发布用 full 这件事的证据强度只等于一片 12 天的 VALIDATION。
   方向上稳的是：运维上下文组（工单+遥测+天气）单独**10/10 轮垫底**（比 staticOnly 还差 0.048–0.141）；
   而桩级历史组相对静态组逐轮差在 ±0.019 内打转（均值 −0.0061）——和第一次盲测"full 略胜"并不矛盾，
   全量的优势本来就薄。
3. **历史变厚也救不了它（本线特有的实验）**：每台桩评测时历史天数中位数首轮 **65 → 末轮 172.5**
   （2.7 倍），纯因果桩先验 AUC 前 3 轮均值 0.7720 → 后 3 轮 0.7803（+0.0083，**小于轮间标准差
   0.0126**）。方向支持"历史越厚越值钱"，但不足以定论——要判定得把窗口拉到一年以上的真实数据。
4. **运营口径反而是稳的**：10/10 轮都满足"精确率 ≥ 2×当轮 VAL 基础率且不超预算"，评测精确率均值
   0.4222、召回均值 0.3832；oracle 十轮均值 0.7737 **没有**跑赢因果先验 0.7768（−0.0031）——
   当天暴露度的可预知部分确实已被历史吃干净，这条不随窗口漂移。

### 改进尝试：分数融合（负结果，2026-09-15）

发布后按规程再试一个方向：把 model / 查表 / 因果先验做 **rank-blend**，权重一律在 VALIDATION 上
取最优冻结，TEST 只算一次、不再回头：

| 融合方案（VAL 选定权重） | VAL AUC | TEST AUC（一次性） |
| --- | --- | --- |
| model ⊕ 因果先验（w=0.5） | 0.7883 | 0.7819 |
| model ⊕ 查表（w=0.25） | 0.7888 | 0.7827 |
| 先验 ⊕ 查表（w=0.75） | 0.7852 | 0.7809 |
| 单柱对照 | model 0.7843 / lookup 0.7868 / prior 0.7856 | model 0.7763 / lookup 0.7812 / prior 0.7820 |

**结论：VAL 上 +0.002~0.004 的领先到 TEST 就消失了**——最好档融合 0.7827 只比"纯因果先验"高
0.0007，在抽样噪声内；查表与先验高度同源，融合等于把同一份信息平均两遍。附一条诚实备注：
均权 model⊕先验⊕用量在 TEST 恰好更高（0.7858），但它不是 VAL 上选出来的档，事后捡它等于把盲测
表翻两次——**不采纳**，只留作"若将来有新 VALIDATION 窗口可复检"的线索。发布口径不变：一行因果查表。

## 已知不足（如实呈报）

- **发布物的定位是"对照 + 排程方法"，不是"最强打分器"**：在能部署的打分器里，一行因果查表就是本线
  当前已知最优（TEST 0.7820）。继续堆模型容量的预期收益是零，这已由十轮符号检验钉死；分数融合也榨不出
  残余收益（见上一节末尾的负结果）。
- **模拟数据里坏桩信号极强**（型号级失败率差、lag1 有真信号、遥测状态与失败相关），真实数据三条都可能
  塌：真实"昨天坏今天好"的维修闭环更快、遥测质量更差、型号差异更小。换真实批次先重跑 `build_panel` +
  泄漏审计再谈一切。
- `heatwave_prev` 恒 0、`temp_c_max_prev` 覆盖 99.4%（−24.2°C 的严冬至 35.1°C，热应力假说在本窗无法检验）。
- 75 台桩 × 178 天的面板，**TEST 域内所有桩都在 TRAIN 出现过**：新桩冷启动没被测过。
- 零方差剔除依赖"稠密面板"这个事实（每桩每天有行），换稀疏面板时 `days_since_last_observed` 一类列会复活，
  届时要重查它们是不是泄漏（测试里钉住了这条前提）。
- 测试层（75 项）顺带修掉过两个"静默吞错"的陷阱：`IGNORED_COLUMNS` 若写成 `frozenset({…dict…})` 会只留键
  丢掉原因；as-of 引擎的 `value=` 自述参数此前不校验、可静默求和错误的列。两处修复不改任何已发布产物
  （特征表 sha 重建后一致：`91a4264727e7…`）。
- 无对外接口：`contracts/` 归负责人，本线**不擅自加端点**，只在下面提案。

## 契约提案（只提案，不改 `contracts/`）

首选交付其实是**离线夜批**：每晚对全部在用桩打分，Top-N（按预算 `ceil(0.25×n)`）落成巡检工单草稿——
本线 `predict --inspect-day` 就是这个产物的离线版，接调度系统只差"谁来审批开工单"。若一定要在线，
建议 `GET /predict/charger-day-reliability?chargerId=&date=` 返回
`{probFailDay, expectedFails, alert, threshold, modelVersion, publishedBatchId, derivedDatasetId}`——
注意口径里必须带 `derivedDatasetId`，本线模型离开 `charger_day_panel_v1` 派生集就不成立。
SQLite 服务库里**不放**本线产物，也不伪造看板数字；两者都需负责人点头。

## 复现

```bash
# 环境：Python 3.13.9 / numpy 2.4.4 / pandas 2.3.3 / scikit-learn 1.7.2 / joblib 1.5.2 / pyarrow 21.0.0
python -m data_analysis.ml.reliability.build_panel          # 聚合派生集 → data_analysis/derived/charger_day_panel_v1/（O_EXCL，拒覆盖）
python -m data_analysis.ml.reliability.features             # 87 列特征表 + 250 行 × 17 量双路径泄漏审计
python -m data_analysis.ml.reliability.train                # 只吃 TRAIN/VALIDATION → bundle + train_metrics.json
python -m data_analysis.ml.reliability.evaluate             # TEST 盲测一次 → evaluation_report.json / .md
python -m data_analysis.ml.reliability.rolling --rounds 10  # 十轮滚动（outputs/ml_reliability_rolling/，可续跑）
python -m data_analysis.ml.reliability.predict --self-check
python -m data_analysis.ml.reliability.predict --verify-report      # 新进程重算，与发布报告逐项比对（本次最大偏差 ≤5e-5）
python -m data_analysis.ml.reliability.predict --charger-id CH-BJ-04-1 --date 2026-05-20
python -m data_analysis.ml.reliability.predict --inspect-day 2026-05-20 --budget 0.15   # 当日 Top-N 巡检清单
python -m data_analysis.ml.reliability.predict --dump-test-table 40
python -m unittest discover -s data_analysis/ml/reliability/tests -t .   # 75 项（无产物/无 sklearn 时自动 skip）
```
