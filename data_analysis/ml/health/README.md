# `ml/health/` · 桩×日"未来 7 天内来修"预测 → 预测性维护巡检排程（第九线）

每晚算一遍：明天开始往后的 7 天里，**这台桩有多大机会被叫去修**（真实维修工单口径，不是
"启动失败"那种用户侧信号）——维护班表按概率从高到低排，预算内排不进的不排。本线把这句话
变成可盲评的模型：**对每台在册桩 × 每个北京日历日 D，预测 `[D, D+6]` 内该桩出现 ≥1 张新维修
工单的概率**（二分类风险分 `prob_ticket7` + 预计工单张数回归），监督标签是
`maintenance_tickets` 里**真实发生的报修记录**（按 `reported_at` 计）。

与前八线的关系：样本单位同第七线（一桩×一日），但**标签换轴了**——第七线学"明天会不会有
技术性启动失败"（用户侧尝试流），本线学"人会不会来修"（运维侧工单流）；同一批 418 张工单在
第七线只是上下文背景，在本线就是答案本身。

| 线 | 标签来源 | 预测什么 | 交付动作 |
| --- | --- | --- | --- |
| `attempt`（第六线） | 单次尝试的失败码 | 这次插枪启动的风险 | App 提示换桩 |
| `reliability`（第七线） | `charging_attempts` 技术失败 | 该桩明天有没有启动失败 | 巡检排程（当日） |
| **本线（第九线）** | **`maintenance_tickets` 真实工单** | **该桩未来 7 天来不来修** | **预测性维护排程（7 天窗）** |

## 泄漏纪律（本线的新东西：一条计数轴、一条修复轴）

决策时点 = 北京日 D 的零点（`day_start_utc`，UTC naive），此后一切不可见。工单表造出
**两条独立的可见性轴**，混用即泄漏：

1. **计数与故障类型走 `reported_at` 轴**：`tickets_7d/30d/90d/prior`、上次故障类型——报修那一刻
   就存在。**"今天 D 当天报的修"不可见**：窗是 `[D, D+6]` 前向、历史是 `[t−wd, t)` 严格早于，
   同一张工单不能既进特征又进标签。
2. **时长与在修状态走 `restored_at` 轴**：`last_repair_hours`、`days_since_last_restore` 只有
   **修完那一刻才存在**（唯一 IN_PROGRESS 工单永不提供时长）；`open_ticket_at_start` = 报修累计 −
   修复累计，是两轴之差。
3. **答案侧全禁**：工单 `status`/`severity`/工时费/配件费、未来那张工单的 `fault_type`、四个原始
   时间戳、`y_ticket7`/`tickets_next7d`/`label_end` 一律禁入（`FORBIDDEN_FEATURES` + 建表断言）。
4. **遥测只看 D−1 及更早**：`prev` = D−1 日，`7d` = [D−7, D−1] 缺格即 NaN（`min_periods=7`，
   覆盖率 96.63%）；当日 D 的任何遥测格子不参与。天气同样只 merge T−1 日城×日聚合
   （`sameDayWeatherNotMerged: true`）。
5. **两条独立路径自证**：随机抽 250 行 × **20 个量**（含标签三件套 `y_ticket7`/`tickets_next7d`/
   `label_end` 的前向窗算术），全表布尔掩码暴力重算（不共用排序/二分/merge_asof/pivot-shift），
   逐条要求 0 偏差——本次实测 19 项 `maxAbsDiff = 0.0`，`usage_energy_kwh_30d` 2.1e−10（浮点
   求和次序级）。测试还**倒放演练**了这套审计：把抽样行的 `days_since_last_report` 改成 999、
   把 NaN 静默补成数值，审计必须当场抛"未来信息泄漏"——防的就是"审计自己瞎了"。
6. **不可部署 oracle 单列对照**：用**含 TEST 标签的全样本**桩级来修率查表打分，TEST AUC
   0.6869——但它和标签自相关（行自己的正类就在表里），只配当"上帝视角"上界，见结果节。

## 运营口径（阈值怎么选、怎么守预算）

冻结规则（只在 VALIDATION 上选，TEST 只验不改）：**精确率 ≥ 2×VAL 基础率（0.41667）且逐日提醒
≤ 当日在册桩数的 25%**（`ceil(0.25×75)=19` 条/天），满足者中取召回最大；无档满足则退回最高
精确率档并**如实标注**（不假装达标）。分位数网格 50 档、至少 30 条告警才参选。
实测冻结阈值 **0.36665**。VAL 侧达标（精确率 0.4259 ≥ 0.41667，216 条告警 / 12.0%）；
**TEST 侧没达标**（见下），阈值不挪。

> **本线未新增任何数据**：样本、标签与全部特征都是对发布批次 clean 表的只读确定性聚合。

模型跑赢**全部可部署基线**：vs 查表 +7.43%、vs 桩先验 +3.11%、vs 只用负荷 +7.88%——但赢幅
和第七线式的"被查表吃掉"之间，本线站在"赢了、赢得不多"这一格。**容量发现**：16 组合
（4 组×4 档）里 **stump3（max_leaf_nodes=3，lr 0.03，400 轮，叶 ≥100 样本）四组全胜**——
3 叶树就吃满信号，深树只会过拟合 TRAIN（0.6866）；发布模型是"几乎纯加法"的浅树。

**必须如实报告的负结论（本线比第八线多）**：

1. **冻结阈值在 TEST 上不达标**：0.36665 下 TEST 告警 257 条（13.71%）、精确率 **0.323** <
   TEST 侧同规则目标 0.3851（2×TEST 基础率），召回 0.2299、F1 0.2686。达标标志是在 VAL 上
   冻结的（`targetMet: true`），TEST 复核失败已写进报告「诚实补记」并**不挪阈值**。预算侧守得住：
   19 条/天的上限 25 天 **0 天超**（日均 10.28、最多 12）。
2. **full 组比 staticOnly 差**（TEST 0.5826 vs 0.6219）：工单史（ticketOnly 单组仅 **0.5424**）和
   运营信号（opsOnly 0.6081）拼进来**稀释**了桩属性×天气的低阶结构；VAL 上四组排序
   （static 0.6097 / full 0.5307 / ticket 0.5305 / ops 0.5262）与 TEST 同向。**"报修史"在本批仿真里
   几乎不含未来信息**——工单间隔接近无记忆（p50 16 天），刚修完的桩并不更容易再来。
   发布模型（staticOnly）因此**不含任何工单史特征**，给运营的直译是：这批数据不支持
   "盯修过的桩"，只支持"盯对型号、对天气、对站型的桩"。
3. **概率头部没有排序头部赢得多**：logLoss 0.49204 / Brier 0.15696 与三级查表（0.49201 /
   0.15613）**打平甚至略输**；十分位校准整体**系统性偏高**（最低桶 0.1601/0.1223，最高桶
   0.4387/0.3750，中间桶实测 0.0688–0.2727 乱序）。排序是真收益，概率当"维护优先级"用没问题、
   **当"来修百分比"直接对外报价要小心**。
4. **张数回归输给最便宜的表**：TEST 工单张数 MAE 模型 0.343 vs 全局均值 0.344 vs **TRAIN 查表
   均值 0.334**——备件预算口径请按查表走，别用模型（如实报，不挑好看的）。

6. **oracle 天花板本身不高**（0.6869，且含自标签膨胀——与因果桩先验差 +0.0837 主要是行自己

   不是特征不够多。想要真信号得上"人工维保动作记录/更换部件记录"这类现在不存在的表。

## 十轮滚动重训研究（`rolling.py`）

折规则：评估窗 = 可用日序列第 `48+8r` 位起 14 天；训练行取"真实日历距离窗起点 ≥7 天"之前
（purge 语义与主链一致），**TEST 域日历一律不进**（每轮断言）。口径警告（写进产物）：特征组与
容量已在 VALIDATION 上被选过，轮次数字有乐观偏差，**不能当盲测报告**。

| 指标 | 结果 |
| --- | --- |
| 模型（staticOnly|stump3）逐轮 AUC | 均值 0.5852，范围 **0.5148–0.6689**（r0 .6308 … r9 .6199） |
| vs 同轮重拟合查表 | **7/10 胜，符号检验 p = 0.34375 —— 统计上不算数**（r1 输 −0.0663 最疼）；逐轮平均增益 +0.0312 |
| vs 同轮因果桩先验 | 9/10 胜，p = 0.021484 |
| 工单史组随"史变厚" | ticketOnly 均值 0.5386、后 5 轮反而比前 5 轮 +0.0338、spearman +0.14——**变厚没变值钱** |
| 运营组随时间 | opsOnly 均值 0.5759、前后差 +0.0006——不随时间增值也不 decay |
| 冻结阈值跨轮 | 达标（≥2×基础率）仅 **2/10 轮**；逐轮精确率 0.125–0.5275；**25 个预算日 0 天超**（第 5 轮甚至 0 告警——分数整体低过阈值） |
| 第 7 轮特例 | 评估窗跨过 TRAIN/VAL 日历边界、段尾 purge 使窗口只剩 8 天（n=600），如实记录在轮次 JSON |

一句话：**盲测那次"跑赢全部基线"，在 10 个时间窗里只是"大多数窗赢桩先验、赢查表赢不稳"**
——本线信号的真实强度就是"薄"，报告与滚动互相印证，不各说各话。

## 已知不足（如实呈报）

- **TEST 比 VAL 好**（0.6219 vs 0.6097）是本次抽样的运气，不是趋势——滚动轮间 σ 就摆在那儿；
  第 8 节数字一律以"区间"心态读。
- **站级/组内小样本切片不单独下结论**：station 25 桶每桶 n=75、AUC 0.29–0.99 之间乱跳，
  是抽样噪声主导，报告里保留原始值但不引用任何单站做卖点；"没修过（无记录）"桶 n=1 直接不报 AUC。
- **遥测零功率列是模拟数据的先天负结果**（恒 0），真实批次里这两列可能复活成最强健康特征
  （"挂着充电却充不进"正是桩病的样子）——换真实批次第一件事就是看这列活不活。
- 418 张工单 ÷ 178 天 ÷ 75 桩 = 日均 0.031 张的**稀疏事件流**，且 severity 恒 MEDIUM、无部件/
  人工明细；"7 天来修概率"在本批数据里的信息天花板由这个密度钉死（oracle 也只有 0.69）。
- **维护动作本身没有数据**：修没修好之后风险怎么变（"换件重启"假设）只能用 `postRepairAge`
  分桶间接看（修完 ≤14 天均值分 0.2986 vs >45 天 0.2430），无真实回访表可验证。
- 无对外接口：`contracts/` 归负责人，本线**不擅自加端点**，只在下面提案。

## 契约提案（只提案，不改 `contracts/`）

首选**离线日批**：每晚对 75 台桩各打一个 `prob_ticket7` + `expectedTickets`，按当日预算
（≤25%×在册）出巡检班表——`predict --schedule-day` 就是这个动作的命令行版（2026-05-10 实测：
阈值命中 10 台 < 预算 19，榜首 CH-SZ-01-2 0.4602）。若一定要在线：
`GET /predict/charger-health?chargerId=&date=` 返回
`{probTicket7, expectedTickets, flagged, threshold, modelVersion, publishedBatchId}`。
SQLite 服务库里**不放**本线产物，也不伪造看板数字；都需负责人点头。
