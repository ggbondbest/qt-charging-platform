# `ml/overstay/` · 充电完成后占桩超时预测 → 移车提醒 / 排队优先调度（第八线）

一场会话快充完的时候算一遍：这辆车的车主充完电大概率会不会继续占着桩（≥30 分钟），
值不值得在充满前推一条移车提醒、要不要把这位"预计快超时"的司机排进优先叫号队列。
本线把这句话变成可复核的模型：**对每一场已经开始的充电会话，在 `started_at` 一刻预测
`unplugged_at − ended_at` 会不会 ≥ 30 分钟**（二分类风险分 + 预计超占分钟数回归）。

与已有七线的关系：样本单位回到"一次会话"，但决策时点比第五线（排队风险，决策在**入队**）
晚、比第一直觉早——**在起充那一刻，本场会话的结束、拔枪、费用全都还不存在**，而本线的标签
恰恰长在"结束之后"。这造成本线独有的**双时间轴**问题（见下节），也是它和前七线最根本的差别。

| 线 | 样本单位 | 决策时点 | 交付动作 |
| --- | --- | --- | --- |
| `queue`（第五线） | 一次排队请求 | 入队时 | 这次会不会放弃/要等多久 |
| `attempt`（第六线） | 一次插枪尝试 | `attempted_at` | 这次启动的技术风险 |
| `reliability`（第七线） | 一桩 × 一日 | 当日起点前 | 明天巡检哪几台桩 |
| **本线（第八线）** | **一次充电会话** | **`started_at`（刚起充）** | **充满前推移车提醒 / 排队优先调度** |

## 泄漏纪律（本线的心脏：两套时间轴）

决策时点是 `started_at`，而标签长在 `unplugged_at` 上。于是每个历史量都要先回答
"**它在起充那一刻存在吗**"：

1. **会话计数走 started 轴**：某用户/某站到此为止充过几场——上一场**一开始**就可见。
2. **超占数值走 unplugged 轴**：上一场占没占、占多久——**等他拔枪那一刻才存在**。
   `user_over_rate_prior` 之类若错用 started 轴，就会把"本场结束之后才知道的事"喂给本场，
   这是本线唯一真正的新式泄漏，`global_prior_at` 因此把事件轴与查询轴拆成两个参数，
   错配直接在签名层面不可能。
3. **答案侧全禁**：`over_min`/`y_over`/`duration_min`、`ended_at`/`unplugged_at`、`status`/`stop_reason`、
   费用能量 SOC 五费率列、`queue_id`/`queue_status`/`joined_at`/`resolved_at`/`campaign_id` 等进
   `FORBIDDEN_FEATURES`。诚实量化为什么禁：答案侧列与标签的 Spearman —— `parking_fee_cents` **0.442**
   （停车费按占桩时长收，它就是答案的马甲）、`energy_wh` −0.104、`total_fee_cents` −0.093、
   `end_soc_pct` −0.01。
4. **两条独立路径自证**：随机抽 250 行，用全表布尔掩码（不排序、不 merge_asof、不复用引擎）
   独立重算 **13 个跨轴量**，逐条要求 0 偏差——本次实测 `maxAbsDiff` 全部 **0.0**。
5. **不可部署 oracle 单列对照**：真用本场充电时长打分 TEST AUC **0.7420**，而决策时点就能算的
   计划时长只有 **0.7717**——**替身不输 oracle**。"这单要充多少度、桩有多大功率"在起充前就把
   单子体量说清了，本线的高 AUC 不吃任何 `ended_at` 之后的信息。
6. **`planned_hours` 的单位口径**：`target_value` 是用户起充前设定的 ENERGY 目标，**单位 Wh**
   （本表 500–77,573 Wh，`target_mode` 恒为 ENERGY）。折算式 = Wh/1000 ÷ 桩额定功率 kW，取值
   0.009–10.9 小时；表内实测取值若超 24h 建表直接炸。这条单位口径出过一次真事故，见"已知不足"。

## 运营口径（阈值怎么选、怎么守预算）

冻结规则（只在 VALIDATION 上选，TEST 只验不改）：**精确率 ≥ 2×VAL 基础率（0.18022）且逐日提醒
≤ 当日开始会话数的 25%**（`max(1, ceil(0.25×n_d))` 按日算），满足者中取召回最大的阈值；无档满足
则退回最高精确率档并**如实标注**（本线未触发退回）。实测冻结阈值 **0.023338**——基础率才 9%，
概率分布挤在低段，阈值长得像小数是正常现象。

**必须如实报告的负结论**（两条，都不利于本线自己）：

1. **跨轴历史与排队运营没有独立增量**：消融表 TEST 上 `staticOnly`（26 列场景）0.8991 **反超**
   `full`（55 列）0.8959（差 −0.0032）；`historyOnly` 单组 0.7959、`opsOnly` 单组 0.6907。
   发布组是 VAL 上以 +0.0010 的差距险胜后冻结的，TEST 上这个差距翻了号——**在 ±0.004 内，
   视为零**。给运营的原话：本批仿真里占桩超时几乎完全由场景（接口/功率/车型/站型）决定，
   "用户习惯"和"当时排没排队"没有场景之外的信息；真实数据若习惯显著，`historyOnly` 组就是现成的量尺。
2. **朴素"上次超时"≈随机**（0.5095）：个人占桩习惯这条直觉在本批数据里根本不成立——
   与结论 1 互证，也预防上线后有人拿"惯犯名单"当提醒策略。

**越预算的负事实（不藏）**：TEST 告警率 29.18% 越过了 25%/日的口径——30 天**每一天**都超

回归分（"预计还会占多少分钟"）与分类分几乎逐档重合——两个模型在排序上就是同一件事，
运营只需要挑一种话术。10% 档最实用：**每天提醒 1/10 的会话，抓到近八成超时**。

**提醒摊在场景、不摊在惯犯**：5,757 条告警摊在 3,378 个用户（当日在网 5,409 人）与全部 25 座站，
最大单站只占告警 8.81%（≈1/25 均摊），最大单用户占 0.12%，超时正类摊在 1,533 个用户头上、
Top-10 用户合计仅占正类 1.73%——**"给惯犯打标签"这条路线在本批数据里无路可走**，动作应按

**组内切片才是真本事**：若 AUC 全靠"大单更容易占桩"，同一计划时长档内分数应失去区分力。
实测计划时长五分位内 AUC = 0.654 / 0.558 / 0.744 / 0.870 / 0.971——档档大于 0.5，体量解释不掉；
按"上次是否超时"切：上次没超时 0.889（n=17,945）、上次超时 0.944（n=1,779）。
与基线分的秩相关（Spearman）：回归 .2913、计划时长 .2716、oracle .256、查表 .1562、
站点先验 .1336、**用户先验 −.0972**——模型和所有便宜口径排出来的大都不是同一批会话。

**校准**（TEST 十分位，预测/实测）：0.0135/0.0167 → … → 0.0248/0.0248 → 0.0332/**0.0188** →
0.7229/0.7238。基础率 9% 的场景下九个低桶概率挤在 1–3% 且与实测贴合，最高桶几乎完美；
第 9 桶轻度高估（+0.014）。概率当"超时可能性"报出去是本批数据里少见地**可以直报**的量。

**回归（预计超占分钟）**：TEST MAE 模型 **9.118** vs 训练均值 26.362 vs 因果用户先验 25.87 vs
TRAIN 查表均值 25.929——分钟尺度同样全赢，可直接支撑"提醒之外还省了多少桩位·分钟"的测算。

**单日演练**（`predict --remind-day 2026-05-20 --budget 0.15`）：当日 638 场会话发 96 条提醒，
其中 54 场真超时（精确率 0.5625、召回 0.794；单日抽样，与全窗口径自洽）。

## 十轮滚动重训研究（`rolling.py`）

折设计与第五、六、七线完全一致：warmup 58 天起，每轮拟合窗后 12 天评测、窗尾 12 天选特征集与
阈值，58 + 12×10 = 178 天**正好铺满** `mlSplits` 全窗。每轮 JSON 以 O_EXCL 落盘可续跑。口径警告：
这些折**重复用到**了上面那次盲测的 TEST 窗口，轮次均值**不是盲测指标**，只回答本线自己的四件事。

| 同轮三级查表基线 | 0.7805 | 0.0098 | 0.7747 | 0.7682 |

四个问题的答案：

1. **赢廉价基线是结构性的**：逐轮增益 vs 查表 +15.23%（σ 1.40）、vs 计划时长 +16.22%（σ 1.72），
   **10/10 轮全胜**，符号检验各 **p ≈ 0.0020**。第七线式"查表吃掉一切"在本线不成立。
2. **习惯增量为零是稳的**：`historyOnly − staticOnly` 十轮**全为非正**（−0.078 ~ −0.105）；
   `opsOnly − staticOnly` −0.176 ~ −0.232；`full − staticOnly` 在 +0.0079 ~ −0.0033 打转
   （6 正 4 负）。"按场景设计、不按个人画像设计"可以当结论用。
3. **用户历史变厚在缓慢变值钱（本线唯一的、带保留的正面发现）**：评测会话的用户历史场次中位数
   首轮 9 → 末轮 23，纯用户先验 AUC 前 3 轮均值 0.5969 → 后 3 轮 0.6172（漂移 +0.0203，
   **大于轮间 σ 0.0127**）。方向值得上线后跟踪，幅度不足以现在就下结论。
4. **运营口径稳**：10/10 轮阈值满足精确率+预算口径（0.0214–0.0251），提醒率均值 25.14%；
   oracle 十轮均值 0.7451 **没有**跑赢计划时长 0.7738——替身不输真身也不随窗漂移。
   每轮 VAL 选组：full 6 次、staticOnly 4 次（后 4 轮连选 static，与 TEST 上 static 反超同向）。

## 已知不足（如实呈报）

- **`planned_hours` 单位事故（开发期自查出，已修复）**：第一版把 `target_value`（Wh）当成 kWh
  折算，列大了 1000 倍。该列只走序数分桶，单调换算**不改任何指标**（重建前后 AUC 逐位一致），
  但名字与标签口径是假的——`predict --remind-day` 的人工目检报出"计划充电 7,626 小时"才暴露。
  修复 = ÷1000 + 建表 24h 上界断言 + 测试公式钉死（`test_planned_hours_units_are_pinned`），
  旧产物整体改名归档（`ml_overstay_v1_plannedhours_unitfix/`）后全链重建。教训已写进测试文档串。
- **写测试时修掉两个潜在缺陷（均不改变已发布产物）**：`global_prior_at` 的事件轴前缀数组在
  "查询晚于一切事件"时索引越界（本批数据最后一场拔枪总在最后一场开始之后，实测到不了），
  扩了一格"全部可见"；`attach_user_history` 一行无用的死代码。两例都有测试钉住。
- **冻结阈值在 TEST 上逐日越预算**（29.18% vs 25%，30/30 天超）——并列分块所迫，见上节；
  修复属于运营侧随机截断，模型发布前无法解决，已在报告 JSON 中逐项给出。
- **TEST 段新面孔只有 3 行**（无用户历史可看；不可见用户 18 行、不可见站 0 行）：
  **冷启动场景没有被盲测覆盖**，十轮滚动同样如此。上线初期真实新用户占比会更高，先按
  "无历史→纯场景组"降级处理，这恰是 staticOnly≈full 给的底气。
- **模拟数据的先天口径**：排队等待恒 5.0 分钟、活动折扣恒 300 分、变压器恒 360kW——真实批次
  这些列会复活且可能带真信号；占桩行为本身是生成器按场景规则造的，"习惯无增量"这条负结论
  **不能外推到真实世界**，它的正确用法是量尺。换真实批次先重跑全链再谈一切。
- 25 座站、6,000 用户、178 天——**站和用户全在 TRAIN 出现过**，站点级新实体冷启动没被测过。
- 无对外接口：`contracts/` 归负责人，本线**不擅自加端点**，只在下面提案。

## 契约提案（只提案，不改 `contracts/`）

首选交付是**会话内事件驱动的推送**：在 `ended_at` 前 N 分钟（N 由回归分给预计剩余分钟决定）
对高风险会话推移车提醒——本线 `predict --remind-day` 就是这个动作的离线版，
只差"谁来触发推送"。次选：叫号调度里给 `overstayRisk ≥ 阈值` 的在场会话降后排序权。
若一定要在线：`GET /predict/session-overstay?sessionId=` 返回
`{probOverstay, expectedOverstayMinutes, remind, threshold, modelVersion, publishedBatchId}`
——**没有** `derivedDatasetId`：本线模型不依赖任何派生数据集，只依赖发布批次 clean 表（与第七线
的契约提案差一个键，这是刻意的）。SQLite 服务库里**不放**本线产物，也不伪造看板数字；都需负责人点头。
